# Stage 08 — automation
Local prototype. Default stopped on every restart. Rules start disabled. Every trigger creates a two-minute approval request; there is no unattended physical execution. Simulation is default and never contacts devices. No AI-generated commands, MQTT publish, arbitrary service names, locks, heaters, alarms or other safety-critical targets.
## Setup
Set HS_AUTOMATION_ADMIN_TOKEN to a random secret of at least 32 characters (generate with node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"). Set HS_AUTOMATION_LIGHTS to a JSON array of exact light entity IDs, e.g. ["light.demo"]. Start with npm run start:configured and enter the token in the Automation panel; held in page memory only. Never commit secrets. Use simulation first. For live control explicitly set HS_AUTOMATION_LIVE=1, HS_AUTOMATION_HA_URL=https://... and HS_AUTOMATION_HA_TOKEN (separate credential, least privilege available). Only HTTPS, verified certificates, no redirects. Home Assistant credentials may have wider permissions upstream; app restricts its own requests. Do not map safety-critical lighting. Keep server on localhost; token is not complete multi-user authentication.
## Rules
Daily UTC minute schedule (no catch-up if offline), or a fresh good sensor value above/below threshold. Conditions require online device and <=5-minute age, trigger on entry, rearm on valid false sample; demo sensors prohibited in live mode. Five-minute per-rule queue cooldown. Create, enable, disable, arm, approve/reject. Rule limit 100. One in-flight command and a one-minute global cooldown measured from approval time. Approval expires after two minutes and condition is rechecked. Energy-saving example: high site power -> propose turning off an explicitly designated nonessential light. No claim of guaranteed savings.
## Emergency
Stop disarms scheduling, cancels pending approvals and aborts local in-flight request. Cannot undo a command already accepted by Home Assistant. Non-success HTTP response, transport timeout or restart during execution is uncertain, never automatically retried. A successful HTTP response is not physical state confirmation. Manually inspect device state. Restart always disarms and cancels pending requests.
## Persistence
Migration 2 adds automation_state, automation_rules, automation_jobs, automation_audit. Audit records local administrative events and execution outcomes; not tamper-proof and not identity-attributed. Jobs and audit history displayed most recent 100; retention not implemented. Single process only.
## API
GET /api/automation; POST /api/automation/rules, /enable, /stop, /approve, /reject. All require bearer admin token and local host/origin checks. JSON request max 8KiB. Existing AI remains read-only. Tests use mocks, no actual hardware.
